1. Foundations: understand the device before coding

1.1 What is a leadless pacemaker?

A leadless pacemaker is a small implant placed inside a heart chamber, generally delivered through a catheter via a blood vessel. Unlike a conventional pacemaker, it has no separate pulse generator under the chest skin and no electrical leads running from that generator to the heart. It senses cardiac electrical activity and delivers pacing therapy for the conditions it is designed to treat.

1.2 Key terms that must not be confused

Term

Plain-language meaning

What it means for your app

Heart-rate measurement or trend

A rate value or summary over some time period.

Can be charted if the source sends a valid measurement and timestamp.

ECG / electrogram waveform

A sampled electrical signal from the heart; a surface ECG and an implant electrogram are not automatically equivalent.

Requires waveform data, sampling information and signal interpretation that match the model.

Prediction of a future clinical event

A model estimates future risk over a defined time horizon, based on validated predictors and outcomes.

Requires a suitable labelled dataset and independent clinical validation; heart rate alone is insufficient.

1.3 What your app is trying to achieve

Show available heart-rate and device information in a clear, time-stamped dashboard.

Analyze suitable ECG waveforms or documented rhythm events, if those data are available.

Identify unusual changes and generate explainable research flags for clinician review.

Ultimately investigate early warning for a specific defined outcome, but only after suitable data and clinical validation exist.

Scope boundary

A pacemaker monitors and treats specific rhythm problems; it is not a complete cardiovascular sensor. An app cannot infer every heart attack, heart-failure episode or cardiac emergency from a rate number alone.

2. System architecture: keep data sources separate from analysis

The core design choice is to keep the data source separate from the analysis. Every observation—simulated or public ECG—must carry a source label. A single analysis engine may accept several data sources only after each source has been converted into a documented common format.

2.1 A common data record

A common schema keeps the dashboard separate from source-specific details. Use only fields actually available from the source. Missing information must be represented as unavailable—not zero, not “normal,” and not inferred from an unrelated field.

{

  "patient_key": "DEMO-001", "observed_at": "2026-10-10T10:00:00Z",

  "source_type": "simulation", "device_family": "unknown",

  "signal_type": "heart_rate_trend", "heart_rate_bpm": null,

  "rhythm_event": null, "pacing_percent": null,

  "battery_status": null, "data_quality": "valid",

  "is_simulated": true

}

2.3 Recommended software architecture

Source adapters: simulator and public ECG reader.

Normalization: convert timestamps, units, event definitions and provenance into the common schema.

Quality gate: check missing values, duplicates, stale transmissions, time-zone problems and unexpected units.

Analysis: compute descriptive trends and run separately validated research models.

Presentation: show the original source, last observation time, uncertainty and reason for each research flag.

3.4 Build the first dashboard using synthetic observations

Create a file called app.py and paste the complete starter code below. It creates a fictional one-hour heart-rate trend and offers a basic scenario selector. This is intended only to test the dashboard, labels and data flow; it is not a clinical simulator and must not be used to set patient thresholds.

from datetime import datetime, timezone

import numpy as np

import pandas as pd

import plotly.express as px

import streamlit as st

 

st.set_page_config(page_title="LeadlessGuard AI", layout="wide")

st.title("LeadlessGuard AI")

st.warning("DEMO ONLY: all values are synthetic, not patient or implant data.")

scenario = st.selectbox(

    "Choose a software-test scenario",

    ["Stable demo", "Sustained rate change", "Missing observations"]

)

rng = np.random.default_rng(7)

minutes = np.arange(0, 60, 1)

rate = 72 + 2*np.sin(minutes/7) + rng.normal(0, 1.2, len(minutes))

if scenario == "Sustained rate change":

    rate[35:] += 18

if scenario == "Missing observations":

    rate[42:48] = np.nan

 

df = pd.DataFrame({"minute": minutes, "heart_rate_bpm": rate})

df["source_type"] = "SIMULATION"

df["is_simulated"] = True

st.caption("Source: SIMULATION | The pattern is fictional and has no clinical meaning.")

left, right = st.columns(2)

with left:

    st.metric("Latest sample", "Unavailable" if pd.isna(df.heart_rate_bpm.iloc[-1])

              else f"{df.heart_rate_bpm.iloc[-1]:.0f} BPM")

with right:

    st.metric("Data source", "SIMULATED")

fig = px.line(df, x="minute", y="heart_rate_bpm",

              labels={"minute":"Minutes from start", "heart_rate_bpm":"BPM"},

              title="Synthetic heart-rate trend")

st.plotly_chart(fig, use_container_width=True)

if df.heart_rate_bpm.isna().any():

    st.error("Some observations are missing: do not interpret gaps as normal data.")

st.subheader("Data preview")

st.dataframe(df, use_container_width=True)

st.caption("Prototype started at: " + datetime.now(timezone.utc).isoformat())

Run it from the project terminal:

streamlit run app.py

4. Track A — bring in real public ECG research data

4.1 Start with reliable public datasets

Use research ECG data to learn signal handling and rhythm classification. Public ECG is not the same as implanted-device telemetry, and its performance should not be assumed to generalize to implanted-device monitoring without appropriate evaluation.

Dataset

What it contains

Appropriate first use

MIT-BIH Arrhythmia Database [5]

48 half-hour, two-channel ambulatory ECG excerpts from 47 subjects, with expert-reviewed beat annotations. Freely available under its stated Open Data Commons Attribution licence.

Learn WFDB reading, annotation handling, waveform plotting and a baseline beat/rhythm task.

MIT-BIH Atrial Fibrillation Database [6]

25 long-term ECG recordings, mostly from subjects with atrial fibrillation.

A separate exploratory task focused on AF-related rhythm patterns, respecting labels and sampling details.

MIT-BIH Normal Sinus Rhythm Database [7]

Long-term recordings from subjects described by the dataset as having no significant arrhythmias.

Example normal-rhythm data; understand population and dataset limits.

4.2 Safe first steps for an ECG record

1. Open the dataset’s official documentation and licence before downloading. Save the dataset citation in README.md.

2. Download only the subset needed for the first experiment. Keep raw files unchanged and place working copies separately.

3. Use WFDB to read a record and annotation file; keep the header because it contains important sampling and channel information.

4. Plot the waveform with the correct time axis and units. Label plots as public research ECG, not implanted device data.

5. Inspect the dataset’s label definitions. Do not guess that one symbol means a disease; consult the database documentation.

6. Create training and evaluation splits by patient or record where possible. Avoid splitting adjacent beats from the same recording across train and test, because that may leak nearly identical information.

4.3 Example: loading a local record

import wfdb

import matplotlib.pyplot as plt

base = "data/public_ecg/100"  # confirm path after downloading

record = wfdb.rdrecord(base)

annotation = wfdb.rdann(base, "atr")  # confirm the annotation suffix

fs = record.fs; n = min(len(record.p_signal), int(fs * 10))

plt.plot([i / fs for i in range(n)], record.p_signal[:n, 0])

plt.xlabel("Time (s)"); plt.ylabel("Amplitude (header units)")

plt.title("Public ECG — research data, not implant telemetry"); plt.show()

print("Sampling frequency:", fs, "| annotations:", len(annotation.sample))

Dataset caution

The code above assumes the chosen record uses an annotation file called atr and has a first channel. Confirm the downloaded record names, signal units, channel labels, and annotation files in the official header and database documentation.

4.4 The first model: keep the question small

Select one task with trustworthy reference labels, such as a documented beat-classification task. Start with a simple baseline and use the reference annotations according to the dataset’s published definitions. Do not jump straight to “predict heart attack” or “predict all cardiac problems.” Those are different clinical questions requiring different outcomes and datasets.

Evaluation metric

What it tells you

Why accuracy alone is not enough

Sensitivity / recall

How many reference-positive examples the model detects.

Missed events may matter even if the overall score looks high.

Specificity

How many reference-negative examples are correctly rejected.

Low specificity can create excessive false alarms.

Positive predictive value (precision)

How often positive model outputs match the reference label.

Affected by event prevalence and the selected population.

Confusion matrix

Counts of correct and incorrect predictions by class.

Shows which categories are being confused.

Calibration / threshold analysis

Whether scores correspond sensibly to observed outcome frequencies, when appropriate.

A ranked score is not automatically a trustworthy probability.

6. Track C — develop the early-warning research engine

6.1 Start with three levels, not one magic AI score

Level

What it does

Evidence needed

Level 1 — Data quality

Detects absent, duplicated, stale or invalid data; tracks when the last transmission arrived.

Unit tests and scenarios for missing, corrupted and delayed inputs.

Level 2 — Descriptive trends

Summarizes rate trends and compares an observation to an appropriate documented baseline.

Correctness tests, documented definitions and clinician review of intended interpretation.

Level 3 — Signal/event model

Classifies a selected ECG pattern.

Suitable labels, held-out recordings, sensitivity/false-positive review and external validation.

Future level — Outcome risk prediction

Estimates a defined future outcome over a defined horizon.

Longitudinal outcome-labelled data; study design; independent validation; calibration; subgroup analysis; clinical utility evaluation and applicable regulatory review.

Figure 4. Each gate requires separate evidence. A good classifier score does not establish clinical utility.

6.2 Define one research question clearly

Use a statement template such as: “Can algorithm X identify ECG pattern Y in dataset Z under evaluation method M?” That can be answered with available public data. By contrast, “Can my app predict a heart attack before it happens?” is not answerable by training a simple classifier on MIT-BIH beat annotations.

6.3 Build explainable research flags

Each output should identify its input source, time window, data quality, algorithm version, finding and limitations. Example language for the prototype: “Research flag: sustained deviation from the demonstration baseline in synthetic data; this is not a clinical alert.”

Good output pattern

Avoid

“Trend-change flag: source X, observations from time A to B; rule version 0.1; requires clinical review.”

“Heart attack predicted” based only on a heart-rate fluctuation.

“Data unavailable: no new observation received since timestamp T.”

Showing “normal” merely because no new data arrived.

“Research classifier output: class Y, score S; model validated only on dataset Z.”

Calling the score a personalized clinical probability without calibration and validation.

6.4 Never create clinical alert thresholds by guessing

A threshold used in a demo is a software test parameter, not a medical recommendation. A patient-specific threshold or escalation rule requires an intended use, specialist input and validation. The app should not adjust pacemaker settings, recommend changing medications, or tell a user to delay emergency care.

6.5 Clinical validation is a separate project phase

Choose a specific intended use and outcome before collecting or modeling data.

Specify inclusion/exclusion criteria, reference standard, time horizon and evaluation protocol with qualified clinical collaborators.

Set aside independent patient/record data before tuning models. Avoid leakage from repeated beats or the same person in train and test.

Report sensitivity, specificity, positive predictive value, false alarms per time period where relevant, uncertainty and missing-data performance.

Examine performance across clinically relevant subgroups and different devices / data sources when relevant.

Run prospective or real-world studies only under the appropriate institutional, ethical, security and regulatory pathway.

Important distinction

Detecting an arrhythmia from an ECG is not the same as predicting myocardial infarction, heart failure, cardiac arrest or stroke. Each endpoint needs its own evidence and may require different data.

7. Data governance, security and Indian regulatory considerations

7.1 Data access and consent

Use synthetic data during early software development. Public research data should be used only in accordance with its access terms and licence.

Do not collect identifiable patient data unless there is a documented, lawful and approved purpose, appropriate permissions and necessary safeguards.

For hospital or clinical research, agree in writing who is the data custodian, who may access the data, how long it is kept, and whether it can be used for publications or presentations.

Use pseudonymous research keys rather than names, phone numbers, or hospital IDs where those identifiers are not required.

Keep ethics committee and institutional approvals documented where applicable. Research approval and device regulatory authorization are different questions; one does not replace the other.

7.2 Minimum technical safeguards

Control

Beginner-level implementation

Data minimization

Keep only fields needed for the current test. Do not pull unnecessary identifiers into development folders.

Secrets

Never put passwords, API tokens or private keys in source code or Git. Use environment variables or a secrets manager where applicable.

Encryption

Use encrypted transport for any permitted network service and encrypted storage where required by the data-risk assessment.

Access control

Limit real data to named authorized team members; separate roles and record access.

Audit trail

Record data source, processing step, timestamp, algorithm version and errors without placing identifiers in routine logs.

Backups / deletion

Document backup locations, retention period, deletion method and restoration tests.

Incident handling

Define whom to notify and what to do if data are exposed, corrupted or misrouted.

7.3 India: medical-device software context

CDSCO states that medical devices in India are regulated under the Drugs and Cosmetics Act, 1940 and Medical Devices Rules, 2017, and its definition includes software intended for specified medical purposes. The CDSCO medical-device pages now list a “Guidance document on Medical Device Software under MDR-2017” dated 21 July 2026. Review the current official document and obtain appropriate regulatory advice before developing for clinical use or distribution. [9, 10]

The fact that a software prototype uses AI does not by itself determine its regulatory class. Intended use, claims, functionality, relationship to the medical device, and applicable rules matter. Do not infer a class, licence requirement or exemption from this beginner guide.

CDSCO — Medical Device & Diagnostics (official guidance index) — Check the current Medical Device Software guidance and the linked Medical Devices Rules, 2017.

India Code — Medical Devices Rules, 2017 — Official legal text; use current amendments and notices as well.

FDA — Content of Premarket Submissions for Device Software Functions — A useful technical/regulatory reference on documenting device-software safety and effectiveness; it is not Indian legal advice.

MeitY — Digital Personal Data Protection Act, 2023 — Review applicable commencement notifications and rules rather than assuming every provision commenced simultaneously.

7.4 Emergency and clinical language

The prototype should clearly state that it is not an emergency monitoring service. A research demonstration may contain delays, communication gaps or unavailable observations. Do not promise real-time rescue, uninterrupted monitoring or that the system can rule out an emergency. Patient-facing content must not advise the user to delay urgent care.

10. Beginner glossary

Term

Plain-language definition

Leadless pacemaker

A small pacemaker implanted in the heart without separate electrical leads.

Telemetry

Data sent from a device to another system.

API

A documented software interface that allows systems to exchange information.

SDK

A software development kit containing tools or code for building against a supported interface.

ECG

Electrocardiogram: a recording of the heart’s electrical activity from electrodes on the body.

Electrogram

Electrical signal measured inside a cardiac device system; it is not necessarily identical to a surface ECG.

Annotation

A label attached to a signal segment or event, often supplied by trained reviewers in a research dataset.

Sensitivity

Share of reference-positive examples detected by the model.

Specificity

Share of reference-negative examples correctly rejected by the model.

Positive predictive value / precision

Share of model-positive predictions that are correct against the chosen reference.

Data leakage

Information from the test set or same patient/record unintentionally influences model training or model selection.

External validation

Testing the system on an independent dataset or setting different from development.

Medical-device software

Software that may be regulated because of its intended medical purpose; exact treatment depends on applicable law and intended use.

Use prototype roles such as Viewer, Researcher, Clinician-Simulation and Administrator; role behavior is demonstrative and must not be presented as a certified clinical access system.

VII. Local cybersecurity demonstrations

Test mock sessions, role permissions, local telemetry integrity, replay rejection and audit events using test fixtures; do not connect to real medical devices or claim certified security.

VIII. Research flags and review

Information/warning/critical-simulation states only; thresholds are software-test parameters; labels require source, interval, rule/model version and limitations; outputs are not diagnoses or emergency alerts.

X. Claims to avoid

Do not claim therapy control, direct implant connection, validated diagnosis, prevention of sudden cardiac death or clinical risk prediction. Describe the work as a simulation and public-ECG research prototype.

XIV. Safety and validation position

Document research tasks, risk controls, software tests, privacy, model performance and limitations; clinical claims require independent validation, qualified review and applicable approvals.

XV. Research and technical sources

Keep dataset documentation, software references, cybersecurity guidance and relevant regulatory guidance for research context; verify relevance and currency before making a claim.

32. Track A/C research framework — 20-panel summary

Figure 8. Research and engineering framework for the retained Track A and Track C scope. It is a planning aid, not a regulator-approved clinical protocol.

Panel

Track A/C content

Implementation note

1. Project scope

Simulation-only prototype; no implant connection, therapy control or clinical decision claims.

Keep all device behavior fictional and visible as simulation.

2. Data inputs

Synthetic scenarios and public ECG records with published labels and annotations.

Preserve dataset citations and distinguish synthetic from public data.

3. Signal modules

Synthetic ECG, PPG, SpO₂ and BIA modules with controlled noise and fault scenarios.

Label fictional physiological values clearly; do not imply validated sensor performance.

4. Source labels and schema

Record source type, timestamp, units, quality state and algorithm version.

Represent missing or unavailable values explicitly; never silently convert them to zero.

5. Data-quality gate

Detect missing, stale, duplicate, malformed, noisy or mislabeled records.

Reject or flag questionable inputs before analysis.

6. Define the research question

Choose one defined ECG classification task or clearly scoped descriptive-trend question.

Match labels and endpoints to the available dataset; avoid unsupported clinical outcomes.

7. Public ECG workflow

Read the dataset documentation, annotation meanings, sampling details and licence.

Cite the source, keep raw files unchanged and document any working copies.

8. Signal preprocessing

Document filters, normalization, segmentation and feature extraction.

Test the pipeline for reproducibility and signal distortion.

9. Dataset split

Separate records or participants across training, validation and final testing.

Avoid leakage from adjacent beats or the same record/person.

10. Baseline model

Begin with a simple model on a task supported by trustworthy reference labels.

Do not jump from beat annotations to predicting heart attack or other unlabelled outcomes.

11. Evaluation metrics

Report sensitivity, specificity, precision and a confusion matrix; assess calibration when appropriate.

Add uncertainty and per-class results where possible; accuracy alone is insufficient.

12. Error analysis

Inspect false positives, false negatives, missing-data cases and subgroup performance.

Document failure conditions and avoid unsupported generalization.

13. Trend analysis

Summarize simulated rate, pacing burden, signal quality and time windows.

Demonstration thresholds are software-test settings, not medical guidance.

14. Explainable research flags

Show source, evidence, time interval, algorithm version and limitations for each flag.

Use research-only wording; do not label synthetic outputs as clinical alerts.

15. Local security tests

Use mock telemetry only; test replay, duplicate/out-of-order messages, malformed packets and session faults.

Keep all security demonstrations local and disconnected from real medical devices.

16. Privacy and governance

Prefer synthetic/public data; document access, retention, ethics and permissions for any approved research data.

Minimize identifiers and restrict access in line with institutional requirements.

17. Safety boundary

No therapy control, diagnosis, prescription or emergency guarantee.

Keep all outputs explicitly research-only and avoid implying emergency detection.

18. Clinical validation readiness

Clinical claims need independent data, defined outcomes, qualified review and applicable approvals.

Performance on synthetic/public ECG does not validate clinical monitoring or patient-risk prediction.

19. Research package

Maintain a runnable dashboard, data dictionary, test report, risk register and model card.

Make assumptions, versions, limitations and results reproducible.

20. Go/no-go gate

Demonstrate reproducibility, source labels, passed safety tests and held-out evaluation before widening claims.

Keep the project in research/demo scope until evidence supports any next step.

38. Final go/no-go checklist

☐ Primary React/Vite interface runs locally and all simulated fields carry explicit source labels.

☐ Simulated pacing engine is deterministic, isolated and contains no real therapy commands.

☐ Synthetic ECG, PPG, SpO2 and BIA modules include fault scenarios and test coverage.

☐ Mock telemetry is read-only and tests reject replay, out-of-order, expired and malformed messages.

☐ AI analysis explains evidence, confidence, signals, time window and limitations; cannot change pacing behavior.

☐ Longitudinal views include 1h, 6h, 24h, 7d and 30d and simulated alerts are auditable.

☐ Battery simulation is clearly an engineering model, not actual implant battery prediction.

☐ All eight research scenarios and PASS/FAIL/BLOCKED/NOT TESTED status behavior are tested.

☐ Clinical/risk claims remain research only unless independently validated and required regulatory/ethics approvals have been obtained.

☐ Supplied screenshots and study findings are clearly distinguished from independently verified official product claims.

☐ Current CDSCO requirements, ethics, consent, privacy and CTRI applicability are checked with the responsible experts before real patient research.
